BLOCK

[문제점]

1. **HIGH — 사전 신원 대조와 차단 INSERT 사이에 다른 이름 등록이 끼어들면, 차단한 키가 계속 글을 쓸 수 있다.**
   **파일:라인:** `ops/admission-block.py:249–279`, `relay/migrations/0002_admission_blocks.sql:24–26`
   **실패 시나리오:** `absent` 검사에서 id·지문 모두 0행을 확인한 뒤, 같은 키가 다른 id로 등록되고 차단 INSERT가 실행된다. 등록 트리거는 차단 커밋 **이후** 등록만 막는다. 이미 등록된 다른 id는 `/events`와 이벤트 트리거의 id 검사에 걸리지 않는다. 사후 대조도 추가 참가자를 허용하므로 성공할 수 있다. 공개 중인 시험 릴레이에서 수행하는 3-7의 absent 차단에도 이 창이 있다.
   **고치는 법:** 신원·기대 모양 조건을 차단 INSERT와 같은 원자적 SQL 안에서 재검증하고, 조건 불일치로 0행이면 중단한다. 사전 SELECT 뒤 다른 이름 등록을 끼워 넣는 시험을 추가한다.

2. **MEDIUM — 동시 등록 한 건이 명부 파일의 모든 변경을 성공으로 덮는다.**
   **파일:라인:** `ops/admission-block.py:284–296`
   **실패 시나리오:** `new_rows > 0`이면 실제 차이와 관계없이 `same_files=True`다. 정상 참가자 한 명이 추가되는 동안 차단 참가자가 `allowed_signers`에서 잘못 빠져도, DB 기존 행만 보존되면 rc 0이다. “새 행 때문”이라는 출력 역시 원인을 검증하지 않은 단정이다. r2 H7의 문구 수정으로는 이 판정 누수를 닫지 못했다.
   **고치는 법:** 추가 행으로 설명되는 차이만 허용하거나, 바이트가 달라지면 대조 미완으로 비영 종료한다. “정상 등록 추가 + 기존 서명자 누락”을 동시에 주는 시험이 필요하다.

3. **MEDIUM — RUNBOOK의 원격 등록 catch 검증은 지정된 입력으로 성립하지 않는다.**
   **파일:라인:** `docs/design/key-lifecycle/RUNBOOK-admission.md:28`, `relay/scripts/run-admission.py:66`, `relay/src/index.ts:162–172`
   **실패 시나리오:** 3-7b는 앱 검사를 제거한 사본에서 이미 등록된 `adm-t18-a`를 재등록하고 403을 기대한다. 실제로는 `byId`의 같은 지문 분기에서 **200으로 반환**한다. INSERT·트리거·catch를 전혀 거치지 않는다. 로컬 race 시험은 행 없는 `ghost`를 사용하므로 이 운영 절차 오류를 잡지 못한다.
   **고치는 법:** 차단됐지만 아직 등록되지 않은 B로 id 차단·지문 차단을 각각 검사하고, 403과 참가자 행 0을 확인한다.

4. **MEDIUM — 탐지기는 `next_cursor` 누락을 정상 종료로 처리한다.**
   **파일:라인:** `tools/detect_ours.py:198–200`, `tests/test_detect_ours.py:79–81`
   **실패 시나리오:** 첫 페이지에 알려진 발신은 모두 있고, 다음 페이지에 원장 미기록 글이 있는데 응답에서 `next_cursor`가 누락되면 탐색이 끝난다. `.get()`이 누락과 명시적 `null`을 합치므로 `OK`·마지막 성공 갱신·기존 경보 해소까지 가능하다. 시험 대역은 항상 이 필드를 넣는다.
   **고치는 법:** 필드 존재와 타입을 검증하고, 명시적 `null`만 마지막 페이지로 인정한다. 필드 누락 응답은 불완전으로 시험한다.

5. **MEDIUM — HTTP 본문 수신 실패가 이미 발견한 경보까지 버릴 수 있다.**
   **파일:라인:** `tools/detect_ours.py:85–91`, `tools/detect_ours.py:494–498`
   **실패 시나리오:** 앞 페이지에서 미기록 글을 발견했어도 후속 응답의 `read()`가 `http.client.IncompleteRead`를 던지면 현재 예외 목록으로 잡히지 않는다. 보고·알림 전에 프로세스가 종료되어 발견 사실이 전달되지 않고, 생존 경보까지 기다리게 된다. `HTTPError` 처리 블록 안의 `e.read()` 실패도 빠져나간다.
   **고치는 법:** 정상·오류 응답의 본문 읽기를 모두 감싸 `HTTPException`을 실패 결과로 변환한다. 앞서 수집한 경보와 불완전 사유를 함께 보고하도록 수신 중단 시험을 추가한다.

[논쟁점]

- **판정 누수 — 확신도 높음:** 지정 변경에서 명부·서명 검증·방 판정·2xx `verdict`·목록 `valid`로 차단 상태를 전달하는 경로는 발견하지 못했다. `/events` catch 순서도 설계와 일치한다. 다만 이는 정적 판독 결과다.
- **원격 스키마 검증 — 확신도 높음:** r2 H11은 이름 점검의 부족분을 3-3 실측으로 보완한다고 하지만, 3-3은 participants·events만 검사한다. 체크포인트 INSERT·UPDATE 트리거 본문은 원격에서 검증하지 않는다. 이름 다섯 개 존재를 네 트리거의 작동 증거로 취급하면 안 된다.
- **재실행의 성공 의미 — 확신도 높음:** `ops/admission-block.py:243–247`은 기존 차단 행이 일치하면 사후 대조 없이 rc 0이다. rc 4·5·6 이후 재실행 성공은 이전 대조 실패의 해소를 증명하지 않는다.
- **원격 D1 지원·오류 감싸기·마이그레이션 기록 — 미확정:** 네트워크·실행 금지에 따라 확인하지 않았다. 처분표의 실행 수치를 독립 재검증한 것으로 간주하지 않았다.
