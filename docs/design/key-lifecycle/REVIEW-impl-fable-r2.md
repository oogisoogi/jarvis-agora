REVISE

**검증 한계**: 제약(읽기만·서버 금지)에 따라 아무 시험도 돌리지 않았습니다. 아래는 전부 정적 판독이고, 처분표의 재측정 수치(58/58 · 22/22 등)는 재현하지 않았습니다. HIGH 는 없고, 원격 쓰기 직전 문에 남은 MED 4건이 REVISE 사유입니다.

## [문제점]

### 1. MED — `--not-ours` 가 상주 신원 검사를 통째로 fail-open 으로 되돌린다 (G12 재지적 · G8 부분)
- **위치**: `ops/admission-block.py:226` · `:253` · `:223`
- **무엇이 틀리나**: `--not-ours` 갈래는 `elif ours and …` 라서 신원 파일을 못 읽으면(`ours is None`) 겹침 검사가 건너뛰어집니다. `:253` 의 상주 가동 검사도 `ours and …` 라 같이 빠집니다.
- **실패 시나리오**: `participant.json` 이 없거나 깨진 기계에서 우리 id 를 막으려 하면 `:223` 이 「다른 참가자면 --not-ours」라고 안내합니다. 그대로 붙이면 우리 id 인데도 겹침 검사 0 · 상주 검사 0 으로 본 릴레이 쓰기까지 갑니다.
- **부수**: 새 id 전환 뒤(§7 단계 7-평시)에는 파일이 새 신원이라 옛 id 차단은 `--not-ours` 가 필수입니다. 그때는 오타 대조가 0 입니다(본 릴레이는 DB 대조가 남고, 시험 릴레이는 3-4 에서 미리 넣으므로 실해는 작음).
- **고치는 법**: `--not-ours` 에서도 `ours is None` 이면 중단합니다. 통과는 별도 명시 플래그로만 허용하고, `:223` 의 안내 문구에서 `--not-ours` 유도를 뺍니다.

### 2. MED — 쓰기 명령 자체가 실패하면 「쓰지 않고 멈췄다」고 말한다 (신규)
- **위치**: `ops/admission-block.py:267-268` · `:283-288`
- **무엇이 틀리나**: `written = True` 가 `run(sql)` **뒤**에 있습니다. INSERT 가 원격에서 커밋된 뒤 wrangler 가 시간 초과·망 끊김으로 rc≠0 을 내면 `Stop` 이 `written=False` 로 잡힙니다.
- **실패 시나리오**: 출력은 「중단: d1 execute 실패」 rc 3 인데 행은 들어가 있습니다. 불가역 쓰기의 결과가 「안 썼음」으로 보고됩니다.
- **고치는 법**: `run(sql)` 앞에서 「쓰기 시도함」 표시를 세우고, 그 실패는 「쓰기 결과 불명 — 재실행으로 확인」 전용 rc 로 말합니다.

### 3. MED — 새 안전장치 시험 3건이 그 안전장치를 재지 않는다 (신규 · G13 과 같은 부류)
- **위치**: `relay/scripts/admission.py:227` · `:231` · `:236`
- **무엇이 틀리나**: 셋 다 `rc == 3` 만 비교합니다. 그런데 해당 검사를 지워도 뒤의 다른 중단이 같은 rc 3 을 냅니다.
  - 끝 개행(`:236`): `fullmatch` 를 되돌려도 「기대 모양인데 id 행이 없다」로 rc 3.
  - 우리 id + 다른 지문(`:227`): 교차 대조를 지워도 로컬 본 D1 에 그 id 행이 없어 rc 3. 신원 파일이 없는 기계에서도 rc 3.
  - adm-t 머리(`:231`): `--persist-to` 가 없어, 머리 검사를 지워도 스키마 점검 실패로 rc 3 일 가능성이 큽니다.
- **결과**: G8·G9·G7 수용의 「시험 추가」는 회귀를 잡지 못합니다.
- **고치는 법**: 중단 사유 문자열을 단언하거나 사유별 rc 를 가릅니다. 각 검사를 뺀 변이가 적색인지 1회 확인합니다.

### 4. MED — RUNBOOK 3-3 은 catch 가 보는 오류 모양을 재지 않고, ③은 실행 가능한 명령이 아니다 (G4·T16)
- **위치**: `RUNBOOK-admission.md:22` · `:30` · `DISPOSITION-impl-r1.md:46`
- **무엇이 틀리나 ⑴**: 3-3 은 wrangler CLI 의 오류 문자열을 기록하고 이를 「catch 의 포함 비교 근거」라 적습니다. catch 가 받는 것은 워커 런타임의 D1 바인딩 오류로, 다른 통로입니다.
- **무엇이 틀리나 ⑵**: 3-7 의 HTTP 실측은 전부 앱 층 사전 검사에서 끝납니다. 앱 검사와 트리거의 조건이 같아서 catch 경로에 닿는 요청이 없습니다. G4 의 덕 타이핑은 원격에서 한 번도 재지 않은 채 본 릴레이로 갑니다.
- **무엇이 틀리나 ⑶**: ③ `INSERT INTO events (… from_id='adm-t16-probe' …)` 는 SQL 이 아닙니다. 원격 D1 에서 즉석 작성하게 됩니다.
- **영향**: 표식이 없으면 경합 창에서 401 대신 500 이 납니다(행 0 이라 차단 자체는 유지).
- **고치는 법**: ③ 전문을 적습니다. 3-7 에 하네스의 `RACE` 편집본(앱 검사 제거)을 시험 릴레이에 한 번 배포해 차단 id 새 글 = 401 을 재는 단계를 넣습니다. 안 넣는다면 처분표 §4 에 「바인딩 오류 모양 = 원격 미실측 잔존」이라 적습니다.

### 5. LOW — 사후 대조의 파일 비교는 여전히 동시 등록에 거짓 경보를 낸다 (G11 부분)
- **위치**: `ops/admission-block.py:275` · `:282` · `:137`
- **무엇이 틀리나**: 행 비교는 부분집합으로 고쳤지만 `same_files` 는 완전 일치입니다. 동시 등록 1건이면 `allowed_signers` 가 달라져 rc 4 입니다.

- **고치는 법**: 새 행이 있으면 파일 차이를 「예상된 차이」로 따로 표시하고, `http.client.HTTPException` 도 잡습니다.

### 6. LOW — 꺼짐 상태의 `/health` 는 모든 실패를 「비응답 확인」으로 적는다 (G5 부분)

- **무엇이 틀리나**: 200·ok:true 가 아니면 시간 초과, 500, JSON 아닌 200 모두 건너뜀 + OK + `last_success` 기록입니다. 문구는 「/health 비응답 확인」으로 고정입니다.
- **실패 시나리오**: 켜져 있는데 `/health` 만 일시 실패하면 그 회차는 조용히 OK 입니다.
- **고치는 법**: 「꺼짐 확인」은 404 + 본문 `1042` 만 인정하고, 나머지는 `trial_off_unconfirmed` 불완전으로 올립니다(연속 2회 규칙이 소음을 거름).

### 7. LOW — T14 업그레이드 시험이 「전」 단계 결과를 버린다 (신규)

## [논쟁점]

- **`d1 export` 가 본 릴레이를 잠깐 막는가** (확신 중간): 내보내기 중 다른 질의가 막히는 것으로 압니다. 맞다면 4-0 은 사용자 영향이 있는 단계이므로 시각을 골라야 합니다.
- **`migrations apply` 가 0001 을 다시 돌리는가** (확신 낮음): 원격에 0001 적용 기록이 없으면 함께 돕니다. 0001 은 전부 `IF NOT EXISTS` 라 무해하지만, r1 조언의 `migrations list` 가 RUNBOOK 에 없습니다.
- **스키마 점검은 이름만 본다** (확신 중간): 본문이 잘리면 CREATE 자체가 문법 오류라 이름이 있으면 본문도 온전할 가능성이 높습니다. 본문 확인은 3-3 의 실측이 맡습니다.
- **차단된 상주의 `/register` 반복** (확신 낮음 · 범위 밖 코드): 상주가 403 을 받고 등록을 재시도하는 구조라면 스스로 `reg:all` 을 태웁니다. 본 릴레이 차단 전 상주 정지가 이를 가립니다.
