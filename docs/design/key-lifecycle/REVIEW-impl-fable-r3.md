## 2. 새 결함

**[문제점 1] MED — 0행일 수 있는데 「차단 행은 썼다」고 말한다**
- 위치: `ops/admission-block.py:295-301`, `:319-321`
- 시나리오: 창 안에 같은 키로 다른 이름이 등록된다 → 조건부 INSERT 가 0행으로 **성공**한다 → `written = True` → 재조회(`:297`)가 wrangler 일시 오류로 실패한다 → 「차단 행은 썼다 · 사후 대조 미완」 rc 5. 실제 차단 행은 0 이고 그 키는 계속 글을 씁니다.
- 원인: 예전 `VALUES` INSERT 에서는 "성공 = 행 있음"이었지만 조건부 INSERT 에서는 아닙니다.
- 고치는 법: `written` 을 재조회로 행을 확인한 **뒤**에 세웁니다. INSERT 성공 ~ 재조회 사이의 실패는 rc 6(결과 불명)으로 떨어지게 합니다. 또는 `d1()` 이 버리는 `meta.changes` 로 0행을 직접 판정합니다.

**[문제점 2] MED — registered 조건과 absent 의 id 선점 갈래는 끼어들기 시험이 없다**
- 위치: `relay/scripts/admission.py:322-340`
- 시나리오: `:279-280` 의 `NOT EXISTS` 절에 오타·퇴행이 생겨도 하네스는 초록입니다. 기존 bobalias·carol 시험은 `classify` 에서 멈춰 SQL 조건에 닿지 않습니다. 본 릴레이의 우리 id 차단이 바로 이 registered 모양입니다.
- 고치는 법: 끼어들기 시험 3개를 더합니다.
  - registered + 같은 지문의 다른 이름 등록 → rc 3 · 차단 행 0.
  - registered + 대상 행 폐기(`UPDATE … revoked_at`) → rc 3.
  - absent + 같은 id 를 다른 키로 등록 → rc 3.

**[문제점 3] LOW — 종료 코드 문서가 어긋난다**
- 위치: `docs/design/key-lifecycle/HANDOFF-impl.md:31`, `RUNBOOK-admission.md` 3-3①·3-4·3-7
- 시나리오: HANDOFF 의 종료 코드 목록에 11 이 없습니다. RUNBOOK 의 차단 단계에는 rc 기대값과 rc 3(0행)·5·6·11 처리 절차가 없습니다. 이제 재실행은 0 이 아니라 11 이라, rc 5·6 뒤에 "성공"에 닿는 길이 없는데 사람이 무엇을 대조해야 끝나는지 적혀 있지 않습니다.
- 고치는 법: HANDOFF 에 11 을 더합니다. RUNBOOK 차단 단계에 "기대 rc 0 · 11 은 이전 대조를 손으로 끝낸다 · 3(0행)은 경보·【질문】"을 적습니다.

**[문제점 4] LOW — 3-7 이 B 차단의 id 를 적지 않았다**
- 위치: `RUNBOOK-admission.md` 3-7 과 3-7b
- 시나리오: 3-7b 는 「B 지문으로 막은 `adm-t18-b` 이름」을 전제합니다. 3-7 에서 다른 id 로 막았다면 3-7b 의 "새 키 C 로 `adm-t18-b` 등록"은 차단 대상이 아니어서 201 로 등록됩니다.
- 고치는 법: 3-7 의 B 차단 명령에 `--participant adm-t18-b` 를 명시합니다.

**[문제점 5] LOW — 운영자 0명 가드는 조건문에 없다**
- 위치: `ops/admission-block.py:260-266`
- 시나리오: 사전 확인 뒤 다른 운영자가 폐기·차단되면 현역 운영자가 0명이 됩니다. master 단독 작업이라 창이 좁고, C1 의 원래 범위 밖입니다.
- 고치는 법: 운영자일 때 조건에 "남는 현역 운영자 ≥ 1"을 더하거나, 잔여 위험으로 기록합니다.
