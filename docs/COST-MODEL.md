# 비용·한도 모델 (S4-2 실측 기록)

> 이 문서의 숫자는 **추정이 아니라 실측**이다. 못 잰 칸은 「미측정」이라고 적고,
> **언제 재면 채워지는지**(해소 판정)를 함께 적는다. 빈칸을 그럴듯한 수로 채우면
> 그 수를 근거로 다음 결정이 쌓이고, 진짜 값이 나왔을 때 되돌릴 수 없다.

측정 일시: 2026-08-25 · 측정 방법: GraphQL 응답의 `rateLimit { cost remaining }` 를 직접 읽음
(우리 계산이 아니라 **서버가 매긴 점수**다).

⚠**2026-09-05 운반층 전환 고지**: 아래 §1~§4 의 수치는 전부 **GitHub Discussions 운반층**의 것이다.
릴레이(`docs/TRANSPORT-RELAY.md`)의 한도·비용은 **아직 하나도 안 쟀다** — 릴레이가 정하는 값이고,
그 값이 오기 전에는 여기 어떤 수도 릴레이에 적용되지 않는다.
★특히 §4 의 결론(「매 주기 전 스레드 읽기는 한 명만으로도 한도를 넘는다」)이 **릴레이에서도 참인지는
모른다.** 다만 그 결론에서 나온 설계(watch 는 목록으로 바뀐 것을 먼저 고르고 그것만 읽는다)는
**그대로 유지했다** — 한도가 넉넉해도 필요 없는 왕복을 늘릴 이유는 없고, 값이 나오기 전에
구조를 먼저 바꾸면 되돌릴 근거가 없어진다.

## 1. 한도 (실측)

| 항목 | 실측값 | 비고 |
|---|---|---|
| GraphQL 시간당 한도 | **5000 점** | `rateLimit.limit` |
| 재설정 | 1시간 주기 | `rateLimit.resetAt` |
| REST 한도 | **미측정** | 우리는 GraphQL 만 쓴다. 해소 판정 = REST 를 쓰게 되면 그때 잰다 |

## 2. 질의 한 번의 점수 (실측)

| 질의 모양 | 점수 |
|---|---|
| 스레드 검색(`search … first:10`) | **1** |
| 스레드 읽기(`discussion.comments first:50` + `replies first:50`) | **1** |
| 카테고리 조회 | **1** |
| 스레드 목록(`discussions first:50` / `first:100`) | **1** |
| 무거운 중첩(`comments:100 × replies:100`) | **1** |
| 스레드 목록 × 댓글(`discussions:100 × comments:100`) | **1** |

⚠**이 측정의 경계(반드시 함께 읽어라)**: 위 값은 **거의 비어 있는 저장소**에서 났다.
GitHub 의 점수는 실제로 돌려주는 노드 수에 따라 달라질 수 있으므로, **데이터가 쌓인 뒤의 점수는 미측정**이다.
· 해소 판정 = 스레드 20건·댓글 200건 이상이 쌓인 시점에 같은 질의를 다시 재서 이 표를 갱신한다.

## 3. 우리 연산의 호출 계수 (실측)

| 연산 | 호출 수 | 비고 |
|---|---|---|
| `fetch` (스레드 번호를 모를 때) | **2** | 검색 1 + 스레드 읽기 1 |
| `fetch` (번호를 아는 때) | **1** | 번호 캐시가 검색을 지운다 |
| `collect`(수집+검증) | **2** | `fetch` 와 같다 — 검증은 로컬에서 한다 |
| genesis 생성 | **2** | 저장소 id 1 + 생성 1 |
| 댓글 달기 | **1~2** | 번호를 알면 1, 모르면 검색이 1 더 붙는다 |
| 한도에 걸렸을 때 | 재시도 **포함** | 계수는 「성공한 횟수」가 아니라 「실제로 쓴 횟수」다 |

## 4. 시간당 소요 — 설계 §10 기준(참가자 20 · 스레드 100 · 댓글 2000)

★**이 절은 실측(§2·§3)과 가정(폴링 주기·읽는 범위)을 곱한 것**이다. 가정 부분은 그렇게 표시한다.

| 시나리오 | 계산 | 시간당 점수 | 종류 |
|---|---|---|---|
| 참가자 1명이 60초마다 스레드 목록만 확인 | 60회 × 1점 | **60** | 실측×가정 |
| 참가자 20명이 위와 같이 | 20 × 60 | **1200** | 실측×가정 (한도 5000 의 24%) |
| 참가자 1명이 60초마다 스레드 100건을 전부 읽음 | 60 × 100 × 1점 | **6000** | 실측×가정 — **한도 초과** |
| 알림 후 필요한 스레드만 읽음(스레드 목록 1 + 바뀐 스레드 k) | 60 × (1 + k) | k=2 이면 **180** | 실측×가정 |

⇒ **결론(설계에 되먹임)**: 「매 주기 전 스레드 읽기」는 한 명만으로도 한도를 넘는다.
watch(S5)는 반드시 **목록으로 바뀐 것을 먼저 고르고 그것만 읽는** 모양이어야 한다.
이 문장이 S5-2 의 설계 제약이다.

## 5. 미측정 칸 (빈칸을 채우지 않는다)

| 미측정 항목 | 왜 못 쟀나 | 해소 판정 |
|---|---|---|
| 데이터가 쌓인 뒤의 질의 점수 | 저장소가 거의 비어 있다 | 스레드 20·댓글 200 이상에서 재측정 |
| `threads` 목록 연산의 호출 계수 | 그 코드가 아직 없다(S6-2) | `threads` 구현 후 `GitHubStore.calls` 로 잰다 |
| watch 주기 조회의 실제 점수 | 그 코드가 아직 없다(S5-2) | watch 구현 후 1시간 실사용에서 `remaining` 감소분으로 잰다 |
| 2차 한도(secondary rate limit) 발동 임계 | 일부러 유발하지 않았다 | 유발 없이는 못 잰다 — **재지 않기로 한다**(남의 서비스를 두드리는 시험은 하지 않는다) |
| REST 한도 | GraphQL 만 쓴다 | REST 사용이 생기면 잰다 |
| **릴레이 rate limit·요청 비용** | 선언값은 왔다(계약 §7 · 아래 §7) — **실사용은 아직 안 쟀다**(릴레이 미배포) | 배포 후 ⑴`RelayStore.calls`(재시도 포함 계수)와 ⑵실제 429 발생 지점으로 잰다 · watch 주기 재계산은 그 값이 나온 뒤 |
| **릴레이 J1 왕복 HTTP 호출 수** | 가짜 릴레이 상대로는 **18회**(2026-09-05 실측) — 실물 아님 | 실물 릴레이 상대 J1 재실행 |

## 6. 한도에 걸렸을 때 (구현)

- 429·403(secondary rate limit)은 **벽이 아니라 신호**다 — 기다렸다 다시 한다.
- 대기는 **곱으로** 늘린다(1초 → 2초 → 4초, 최대 4회). 같은 간격으로 재시도하면
  한도가 풀리기 전에 시도를 다 써 버린다.
- 문법 오류·권한 없음은 **기다려도 그대로**이므로 즉시 올린다.
  둘을 안 가르면 ⑴영영 못 고칠 것을 계속 두드리거나 ⑵고칠 필요 없는 것을 실패로 올린다.

클라가 서버 상한을 흉내내면 두 값이 갈리는 날 조용히 틀린다.
