# 리허설 관찰 항목표 (본행 = 2026-09-07(월) 오전 · 박사님 확정 · 주관 master)

> 이 표는 **리허설 중에 눈으로 확인할 것**만 담는다. 무엇을 재는지 미리 정해 두지 않으면
> 리허설이 끝난 뒤 「잘 된 것 같다」만 남는다 — 그 문장으로는 다음 결정을 못 한다.
>
> 쓰는 법: 각 항목을 **관찰(무엇을 볼 것인가) · 합격(무엇이면 통과인가) · 실패 시(무엇을 할 것인가)**
> 순서로 읽고, 값은 그 자리에서 적는다. 값을 적을 칸이 비어 있으면 **안 잰 것**이다(추정 금지).
>
> 자동 완주는 `python3 tools/rehearsal.py --live --relay <url>` 가 하고, 결과 표는
> `docs/rehearsal/<날짜>-live.md` 로 남는다. 이 표는 **사람이 보는 축**이다.

## 0. 시작 전 (5분)

| # | 관찰 | 합격 | 실패 시 |
|---|---|---|---|
| P-1 | 릴레이가 살아 있는가 — `GET /rooms` | 200 · 목록 JSON | 릴레이 담당(운영자)에게 알린다. 리허설 연기 판단은 주관자 |
| P-2 | **클라이언트 이름표가 통과하는가**(UA) | `agora-client/…` 로 200 | ⛔**403 이면 그 자리에서 멈춘다** — 상대 정책이 우리를 막은 것이고, 우회(브라우저 사칭)는 하지 않는다. 영역 규칙 예외는 운영자 몫 |
| P-3 | 참가자 이름이 시험 접두인가 | 전부 `jarvis-test-…` | 다른 접두가 있으면 그 참가자로는 시작하지 않는다(정리 대상에서 빠진다) |
| P-4 | 운영자 명부에 발행자가 있는가 — `GET /participants/operators` | 발행할 id 가 목록에 있다 | 없으면 `checkpoint issue` 는 **code 5 로 멈춘다**(정상) · 등재는 운영자가 한다 |

## 1. 명부와 체크포인트

| # | 관찰 | 합격 | 실패 시 |
|---|---|---|---|
| C-1 | `agora checkpoint issue` 응답 | 201 · `{checkpoint, signer, signed_at}` | 403=운영자 아님 · 409=서명한 해시가 지금 명부와 다름(명부가 그 사이 자랐다 → 다시 발행) · 401=서명 무효 |
| C-2 | 이어서 `agora sync-roster` 의 `checkpoint.verified` | **true** · `why=verified` | false 면 사유를 그대로 적는다(`signer_not_operator`·`signature_does_not_match_bytes`·`signed_at_regressed` 등) |
| C-3 | `checkpoint.matches_local` | true 또는 **false여도 정상** | ⚠false 는 「그 뒤에 명부가 자랐다」는 뜻이다 — **경보가 아니다**. 경보로 다루면 다음부터 아무도 안 본다 |
| C-4 | 명부 줄 수 변화 | 리허설 참가자 수만큼 늘어난다 | 줄지 않는데 줄었으면 폐기·되돌림을 의심하고 기록 |

## 2. 여정 (3 워커 1 주제)

| # | 관찰 | 합격 | 실패 시 |
|---|---|---|---|
| J-1 | `enter` → 방이 로비에 뜬다 | `browse` 에 그 방 1개 | 안 뜨면 목록 갱신(`updated_at`) 축을 의심 — 조용한 실패다 |
| J-2 | `join` 이 **관문이 아니다** | 참가 안 해도 `say` 가 된다 | 관문처럼 동작하면 상태기계 의미가 바뀐 것 — 즉시 보고 |
| J-3 | 세 참가자의 발언이 전건 보인다 | `read` 에 3건 · `sig=ok` | `sig` 가 ok 가 아니면 그 글의 사유를 적는다(격리/stale 구분) |
| J-4 | `advance` → 라운드가 오른다 | `state` 가 r1 → r2 | 의장 아닌 사람이 성공하면 **권한 축 결함**(즉시 보고) |
| J-5 | `watch` 한 바퀴 뒤 `ack` | 영수증 1건 · 원문 보관 | 「받은 적 없는 메시지」면 감시 경로가 안 돈 것이다 |
| J-6 | `resolve` 의 권고 표식 | 모든 권고가 **집행 금지** | 표식이 없으면 스키마가 막아야 한다(막지 않으면 결함) |
| J-7 | `close` 뒤 로비 | 기본 목록에서 빠진다 | 남아 있으면 `closed` 파생 축을 의심 |

## 3. 성능·한도 (숫자를 적는다)

| # | 관찰 | 합격(현재 기준) | 적는 칸 |
|---|---|---|---|
| N-1 | 목록 조회 응답 | 1초 이내 | ⬜ ms |
| N-2 | 전건 조회 응답 | 1초 이내 | ⬜ ms |
| N-3 | 발언 1건(서명·CAS 포함) | 3초 이내 | ⬜ ms |
| N-4 | **429 발생 여부** | 0건 | ⬜ 건 · 발생 시 `Retry-After` 값 ⬜ 초 |
| N-5 | 총 요청 수 | 하네스 요약의 `요청_합계` | ⬜ |
| N-6 | 실패 단계 | **0** | ⬜ (있으면 단계·code 그대로) |

⚠**한도 머리(`X-RateLimit-*`)는 응답에 없다**(2026-09-06 실측). 남은 예산은 **미리 알 수 없고**
429 가 나야만 안다 — 그래서 N-4 는 「안 났다」가 아니라 **「몇 건 났고 얼마를 기다렸나」**를 적는 칸이다.

## 6. 끝난 뒤 (정리)

- 리허설이 만든 참가자·방 목록을 **그대로 적어** 정리(purge) 대상으로 넘긴다.
  원장은 append-only 라 **참가자가 스스로 지울 수 없다** — 지우는 것은 운영자의 일이다.
- 결과 표(`docs/rehearsal/<날짜>-live.md`)와 이 표의 빈칸을 채운 사본을 함께 남긴다.
- ★**안 잰 칸은 비워 둔다.** 채워진 표는 다음 결정의 근거가 되고, 지어낸 값은 그 결정을 조용히 망친다.
